# IFEM Persian Localization Standard

This glossary governs Persian-language IFEM pages. It is intended to keep the Persian edition technically precise and stylistically natural rather than literally translated from English.

| English concept | Preferred Persian | Usage note |
|---|---|---|
| Interface-First Execution Methodology | روش‌شناسی اجرای رابط‌محور | Keep `IFEM` visible with the Persian name on first reference. |
| interface | رابط | Use رابط consistently. |
| boundary | مرز | Prefer “مرز معماری” or “مرز مسئولیت” where context clarifies meaning. |
| contract | قرارداد | Engineering contract, not legal contract. Context should make this clear. |
| verification | راستی‌آزمایی | Use for checking conformance to a defined contract/specification. |
| validation | اعتبارسنجی | Reserve for validation of intended behavior/fitness, where actually meant. |
| check | بررسی / کنترل | Use for lightweight checks, not as a substitute for verification. |
| evidence | شواهد قابل‌بررسی | Prefer this when evidence is machine-checkable or reviewable. |
| execution | اجرا | For implementation activity, “پیاده‌سازی” may be more natural; use “اجرا” for execution/governance concepts. |
| parallel execution | اجرای موازی / پیاده‌سازی موازی | Choose by context and remain consistent within a section. |
| runtime enforcement | اعمال قرارداد در زمان اجرا | Avoid the literal and vague “اعمال در زمان اجرا” when the contract is the object being enforced. |
| AI coding agent | عامل کدنویسی هوش مصنوعی | On first use; “عامل کدنویسی” is acceptable after context is established. |
| scope | دامنه / محدوده | “محدوده” for allowed action; “دامنه” for task/system scope. |
| ownership | مالکیت / مسئول مشخص | Prefer wording that makes accountability understandable. |
| compatibility | سازگاری | “الزامات سازگاری” for contractual requirements. |
| acceptance criteria | معیارهای پذیرش | Use plural where multiple checks are implied. |
| schema | شِما | Keep this established Persian technical transliteration. |
| endpoint | نقطه پایانی (endpoint) | Introduce bilingual form on first use. |
| CI | CI | Keep the acronym; write “راستی‌آزمایی در CI” rather than forcing a Persian expansion. |

## Style rules

- Translate ideas, not English syntax.
- Avoid literal constructions such as “مرز یک شیء طراحی است”. Prefer natural technical Persian such as “مرز، یک عنصر معماری است”.
- Keep official publication titles, DOI values, ORCID, IFEM, BibTeX, RIS, CI, API, and version identifiers unchanged.
- Do not turn “verification” into “validation” unless the English source actually means validation.
- Avoid unsupported claims of adoption, peer review, certification, or industry standard status.
- Persian pages must remain semantically equivalent to the English doctrine, but sentence structure should be native Persian.
