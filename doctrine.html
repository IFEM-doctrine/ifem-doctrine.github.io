IFEM / Doctrine

Parallel work fails at the unspoken boundary.

The doctrine is not a process prescription. It identifies where coordination breaks down, then changes the failure mode before it compounds across a system.

The diagnosis

When engineering teams divide responsibilities without making the boundaries between those responsibilities explicit, they create a shared assumption space. That space is invisible, undocumented, and inconsistent across contributors. As implementation proceeds, each side fills the assumption space differently. The failure does not appear immediately — it appears at integration, when the assumptions are finally compared and found to be incompatible.

The same failure mode applies to AI-assisted engineering. A coding agent that is not bounded by an explicit interface contract will make architectural decisions within its scope that conflict with decisions made by other agents or human contributors working in adjacent scopes. Speed of generation does not reduce this risk — it amplifies it, because more implementation is produced before the conflict is discovered.

The boundary is the coordination mechanism. If the boundary is not explicit, coordination is accidental.

Freeze interfaces before work begins

An interface is more than a type signature or an API route. It is a shared agreement about what crosses a system boundary, who owns each side, how errors behave, and what is permitted to change. When that agreement is frozen, teams can work independently without silently redefining each other's responsibilities.

Core principles

01

Interfaces before implementation

The shape of the boundary between components must be agreed upon before either side is built. An interface defined after the fact describes what was built; it is not an agreement about what should be built.

02

Contracts before coordination

A contract is an interface with enforcement. It specifies schemas, ownership, error behavior, compatibility rules, and acceptance criteria, so coordination does not need to be renegotiated at every integration point.

03

Evidence before acceptance

An implementation is complete when it produces verifiable evidence that it satisfies the contract it was built against. The evidence can be a contract test, schema validation, integration probe, or runtime assertion.

04

Boundaries define authority

Inside a bounded scope, a team or agent has authority over implementation. Outside that scope, it does not. The boundary protects neighboring contributors from unreviewed architectural decisions.

05

Verification coordinates

IFEM replaces integration-as-coordination with verification-as-coordination. Conflicts are discovered at a contract boundary continuously, rather than in a high-stakes system integration event.

The structural contrast

The difference between implementation-first and interface-first work is not a matter of style. It is a difference in when and how coordination costs are paid.

Who the doctrine applies to

The IFEM doctrine is not specific to a role, team size, or technology stack. The coordination problem it addresses appears wherever independent contributors share a system boundary — whether those contributors are human engineers, AI coding agents, or both.

Engineering leaders apply the doctrine by requiring ownership and delivery boundaries before work begins at scale. Software engineers apply it by refusing to treat neighboring components as undocumented moving targets. AI-assisted teams apply it by constraining agents with contracts, scopes, and evidence requirements. Students apply it by learning that architecture is a discipline of boundaries, not simply a collection of implementation patterns.
