IFEM / Method

A controlled path from intent to execution.

IFEM turns architectural intent into constraints that independent contributors — human or AI — can implement, test, and enforce without redefining the system along the way.

01

Define intent

State the system outcome and its constraints before implementation choices take over.

Intent definition is the first and most consequential phase of IFEM. Before any interface is drawn or any contract is written, the system outcome must be stated in terms that are independent of implementation technology. This means specifying what the system must accomplish, what constraints it must operate within, and what trade-offs are acceptable — without committing to how any of those requirements will be met.

Intent that is not documented before implementation begins will be reconstructed from the implementation after the fact. That reconstruction is always incomplete and always biased toward what was built rather than what was needed. IFEM treats undocumented intent as a coordination risk, not a planning shortcut.

Typical outputs

System outcome statement Constraint inventory Accepted trade-offs Scope boundary definition
02

Freeze interfaces

Make dependencies and responsibilities explicit enough for independent work to begin.

Interface definition translates intent into system structure. Each interface specifies a boundary between two components: what crosses the boundary, in which direction, under what conditions, and with what guarantees. An interface is frozen when both sides of the boundary agree on its specification and commit to implementing against it rather than around it.

Freezing does not mean permanent. Interfaces can be versioned and evolved. But a frozen interface is one that cannot be changed unilaterally by either side — any change requires explicit renegotiation and a new version. This constraint is what makes parallel work safe: each side can implement at full speed because the boundary will not shift beneath them.

Typical outputs

Interface specifications Dependency map Ownership assignments Versioning policy
03

Encode contracts

Specify schemas, ownership, error behavior, compatibility rules, and acceptance criteria.

A contract is a frozen interface with enforcement. Where an interface specification describes the shape of a boundary, a contract specifies the rules that govern behavior at that boundary: the schema of every data structure that crosses it, the ownership of each field, the error codes and their semantics, the compatibility guarantees across versions, and the acceptance criteria that determine whether an implementation satisfies the agreement.

Contracts are the central artifact of IFEM. They are the source of truth for every implementation decision made within a bounded scope, the basis for every verification check, and the evidence that independent work can be integrated safely. A system with explicit contracts can be parallelized aggressively. A system without them cannot be parallelized safely at any speed.

Typical outputs

Schema definitions Error catalogs Compatibility matrices Acceptance criteria Contract test suites
04

Execute in parallel

Build behind bounded interfaces instead of inventing shared behavior midstream.

With intent defined, interfaces frozen, and contracts encoded, implementation can proceed in parallel across all bounded scopes. Each team or agent works against the contract for its scope, not against assumptions about what neighboring scopes are doing. The contract is the only coordination artifact required during implementation — no synchronization meetings, no shared implementation details, no undocumented assumptions.

For AI-assisted teams, this phase is where IFEM provides its most direct value. A coding agent operating within a bounded contract cannot make architectural decisions that affect other scopes. Its authority is limited to the implementation of its contract, and its output is evaluated against the contract's acceptance criteria rather than against informal expectations.

Typical outputs

Bounded implementations Contract-aligned code Scope-local test suites
05

Verify evidence

Use contract checks, CI, integration tests, and runtime controls where appropriate.

Verification is the phase in which implementations produce evidence that they satisfy their contracts. The form of evidence depends on the nature of the contract: schema validation for data contracts, contract test suites for API contracts, integration probes for runtime contracts, and formal verification for safety-critical contracts. The requirement is not a specific verification technique — it is that evidence exists and is checked automatically.

When verification is continuous and automated, it replaces the integration event as the coordination mechanism. Conflicts are discovered at the contract boundary, not at the system boundary. The cost of a conflict is proportional to the scope of the contract, not to the scope of the system. This is the structural advantage that IFEM provides over integration-first coordination.

Typical outputs

Contract test results Schema validation reports Integration evidence Runtime assertion logs Acceptance decisions
