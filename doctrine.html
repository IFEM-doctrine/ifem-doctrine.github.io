IFEM / Doctrine

Parallel work fails at the unspoken boundary.

The doctrine is not a process prescription. It is a diagnosis of where software coordination breaks down, and a set of principles that change the failure mode before it compounds.

The diagnosis

When engineering teams divide responsibilities without making the boundaries between those responsibilities explicit, they create a shared assumption space. That space is invisible, undocumented, and inconsistent across contributors. As implementation proceeds, each side fills the assumption space differently. The failure does not appear immediately — it appears at integration, when the assumptions are finally compared and found to be incompatible.

The same failure mode applies to AI-assisted engineering. A coding agent that is not bounded by an explicit interface contract will make architectural decisions within its scope that conflict with decisions made by other agents or human contributors working in adjacent scopes. Speed of generation does not reduce this risk — it amplifies it, because more implementation is produced before the conflict is discovered.

The boundary is the coordination mechanism. If the boundary is not explicit, coordination is accidental.

Core principles

01

Interfaces before implementation

The shape of the boundary between components must be agreed upon before either side is built. An interface defined after the fact is a description of what was built, not an agreement about what should be built. IFEM requires that interfaces are defined, reviewed, and frozen before implementation begins in any bounded scope.

02

Contracts before coordination

A contract is an interface with enforcement. It specifies not only the shape of the boundary but the ownership of each element, the error behavior, the compatibility rules, and the acceptance criteria that determine whether an implementation satisfies the agreement. Coordination without contracts is negotiation that must be repeated at every integration point.

03

Evidence before acceptance

An implementation is not complete when it compiles or when it passes a unit test. It is complete when it produces verifiable evidence that it satisfies the contract it was built against. Evidence may take the form of contract tests, integration probes, schema validation, or runtime assertions — the form is secondary to the requirement that evidence exists and is checked.

04

Boundaries define authority

Within a bounded scope, the implementing team or agent has full authority over implementation decisions. Outside that scope, they have no authority. This separation is what makes parallel work safe: each contributor can move at full speed within their boundary because the contract prevents their decisions from silently affecting neighboring scopes.

05

Verification is the coordination layer

In an implementation-first approach, integration is the coordination layer — the moment when assumptions are compared and conflicts resolved. IFEM replaces integration-as-coordination with verification-as-coordination. When contracts are explicit and evidence is required, the coordination happens continuously and automatically, rather than in a single high-stakes integration event.

The contrast

The distinction between implementation-first and interface-first is not a matter of preference or style. It is a structural difference in when and how coordination costs are paid.

Who the doctrine applies to

The IFEM doctrine is not specific to a role, team size, or technology stack. The coordination problem it addresses appears wherever independent contributors share a system boundary — whether those contributors are human engineers, AI coding agents, or both.

Engineering leaders apply the doctrine by requiring that ownership, integration boundaries, and delivery expectations are made explicit before work begins at scale. Software engineers apply it by refusing to treat neighboring components as undocumented moving targets. AI-assisted teams apply it by constraining agents with contracts, scopes, and evidence requirements rather than relying on the agent's judgment about architectural decisions. Students apply it by learning that architecture is a discipline of boundaries, not a collection of implementation patterns.
